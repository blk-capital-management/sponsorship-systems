# Outreach system audit — 2026-08-16

Scope: `outreach/` (BLK Bridge). Baseline at audit time: **451 tests passing**, commit `5b4cf58`.

Every finding below was verified against the code, not inferred. Line references are to the
state of the tree at the time of writing.

Severity key: **S1** breaks or loses user work · **S2** wastes paid credits or hides failure ·
**S3** drift, dead code, or maintenance cost.

## S1 — Whole-batch abort on a single bad row

`dashboard/services.py:113` raises `DashboardServiceError` on the first duplicate or unusable
firm slug in a batch:

```python
raise DashboardServiceError(f"Duplicate or unusable firm name in batch: {item.firm!r}.")
```

Worse, the insert at `services.py:135` is a single bulk call. `targets.firm_slug` is `unique`
and there is a `targets_domain_unique_idx` on `lower(domain)`
(`supabase/migrations/001_phase_g_dashboard.sql:62`), so if *any one* firm in the batch already
exists, PostgREST rejects the whole statement and every row is lost.

**Impact.** Pasting 30 sourced leads where one is already in the pipeline loses all 30, and the
error message ("Check for an existing firm slug or domain") does not say which one.

**Fix.** Per-row insert with per-row outcomes; return `{accepted, skipped}` with a reason each.
Addressed in this change set.

## S1 — Duplicate detection is exact-match only

The only duplicate guards are `firm_slug unique` and a unique index on `lower(domain)`.
Both are exact string matches.

`scripts/derive_target_status.py:105 normalize_firm()` already implements fuzzy firm-name
normalization — generic suffix stripping, abbreviation folding, parenthetical removal — but it
is used **only** for matching against the Excel CRM, never at intake.

**Impact.** "Sixth Street" and "Sixth Street Partners" both insert as separate targets, each
consuming its own research crawl and its own Hunter credits. Duplicate outreach to one firm is
a reputational risk, not just a data-quality one.

**Fix.** Run `normalize_firm()` at intake and warn on near-duplicates. Addressed in this
change set (as a warning, not a hard block — the operator decides).

## S2 — No retry or backoff on any external call

`contacts/providers/hunter.py:168-171` treats HTTP 429 as terminal:

```python
if response.status_code == 429:
    log.warning("Hunter rate limit hit for %s.", email)
    return VerificationResult(email, 0, "rate_limited", self.name, error="rate_limited")
```

The credit is spent, the rate-limit window is not waited out, and the result is discarded. The
same pattern holds for `common/http.py` crawls and `dashboard/storage.py` Supabase calls — grep
for `retry` or `backoff` across the package returns nothing.

**Impact.** On a batch run against the free tier, a burst of 429s silently degrades a run into
partial results that look like genuine "no contacts found".

**Recommendation.** Bounded retry with jittered backoff on 429 and 5xx only, capped at 2
attempts, and never on 4xx-other. **Not addressed in this change set** — it changes credit
consumption timing and should be measured against the live rate limit first.

## S2 — `HunterProvider.account()` still swallows its own exceptions

`contacts/providers/hunter.py:108-110`:

```python
except Exception as exc:
    log.debug("Could not read Hunter account balance: %s", exc)
    return None
```

Commit `7f97359` ("Make provider failures visible") fixed the *caller* — `hunter_balance()` at
`services.py:551-586` now returns an explicit error string when `account()` comes back empty —
but the underlying swallow is intact, and it logs at `debug`, which is below the default level.

**Impact.** A misconfigured key, a network failure, and a genuinely empty response are still
one indistinguishable `None` at the provider boundary. The UI now says *something* is wrong but
cannot say what.

**Recommendation.** Log at `warning` and attach the exception type to the returned value.
Low risk, but it touches the provider contract that `7f97359` just stabilized, so it is left
for a focused change.

## S3 — The Anthropic call is unwired in production

`drafts/generate.py:653`, inside `generate_draft`:

```python
del anthropic_client  # compose_firm_paragraph intentionally remains unwired.
```

`compose_firm_paragraph` (`generate.py:293-346`) is the **only** LLM call site in the entire
system. It is reached only by tests. Real firm paragraphs are composed deterministically from
sourced alignment hooks.

Two config keys in `config/settings.yaml` describe behavior that therefore does not exist:
`drafts.firm_paragraph.max_validator_retries: 2` and `on_validator_failure: fallback`. There is
no retry loop in `generate.py`.

**This is a deliberate design choice consistent with rule 6, not a bug** — separating research
from drafting is precisely what prevents hallucinated firm facts. It is recorded here because
it is invisible from the outside and materially changes what "efficiency" means:

> **Today the system spends effectively zero LLM tokens in production. Cost optimization here
> means Hunter credits and crawl budget, not model spend.**

**Fix.** Document it in `CLAUDE.md`; remove or comment the dead config keys. Addressed.

`CLAUDE.md`'s pipeline diagram and `config/settings.yaml` both reference files that do not

existing. Anyone onboarding reads the diagram first.

**Fix.** Rewrite the diagram to match reality; delete the dead settings keys; remove the empty
directory. Addressed.

## S3 — Stale comment in `config/email_patterns.json`

The file's `_comment` reads: *"Patterns MUST be derived only from public sources … Never from
LinkedIn."* Every live entry (`bamfunds.com`, `sixthstreet.com`) carries a
`https://www.google.com/search?q=site:linkedin.com…` URL as its `source_url`.

**This is not a rule-3 violation.** It is the documented decision recorded in
`config/settings.yaml` (Jamari's call, 2026-08-13): using a licensed API whose corpus includes
LinkedIn is within rule 3 because BLK is not scraping LinkedIn. The decision is enforced in
code on both sides — `contacts/providers/hunter.py:48` defines `LINKEDIN_SOURCE_MARKERS` with a
`reject_linkedin_derived_sources` toggle, `research/schema.json:23` rejects LinkedIn hosts and
encoded `site:linkedin.com` scopes in research artifacts, and `common/http.py` refuses
`linkedin.com` at the request layer so no scraping path exists at all.

Only the comment is wrong. **Fix.** Correct it to state the actual policy. Addressed.

### One plan change worth recording

The plan called for collapsing `storage.py`'s six `x` / `service_x` method pairs into a single
`service: bool` keyword argument. **That was not done, on purpose.** The class docstring
describes "explicit caller-token and service-token lanes", and `service_*` bypasses RLS. A
boolean flag would make privilege escalation a one-character edit and would hide it at the call
site. The duplication was in the request plumbing, not the interface, so the plumbing was
shared (`_do_select`, `_do_write`) and both public names kept. Same line saving, boundary
intact: 333 → 311 lines.
